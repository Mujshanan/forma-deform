# FDM-06.4 — AniCraft Host Extension and Identity Design

**Status:** Design proposal; pending review and acceptance  
**Milestone:** FDM-06.4 — Host Extension and Identity Design  
**Depends on:** FDM-06.2 Native Integration Contract; FDM-06.3 Host Contract Conformance Plan; FDM-05.4 output contract; M1 persistence/identity contracts; CCC-01.5  
**Host:** `Mujshanan/anicraft`  
**Pinned host source:** `2df7775907d1458ce653e7e6314ec8a5d7d565f5`  
**Scope:** Design only. No AniCraft implementation, FDM runtime change, schema migration, API change or merge is authorized.

## 1. Purpose and decisions

This document resolves the first four FDM-06.3 blockers: persistent document identity, target incarnation identity, host-owned extension placement, and the lifecycle rules for duplicate/import/undo/redo.

The design adopts these principles:

1. AniCraft owns the serialized extension slot, document identity, target-incarnation ledger, mutation lifecycle and transaction boundaries.
2. FDM owns the versioned authored model payload, topology, deformation semantics, and FDM-specific migrations.
3. A target reference is never just an `ElementId`. It is a compound identity scoped to one persistent document and one target incarnation.
4. Runtime freshness epochs are distinct from persistent identity and are never restored backwards by undo/redo.
5. Existing documents without FDM data remain valid and behave as before.
6. Unknown or unsupported FDM data is never silently interpreted, discarded or rewritten by an older implementation.
7. No sidecar is the authoritative store for authored FDM state. The authoritative extension travels with the AniCraft document.

Verified source facts:

- `Document` is serializable and deserializes through the explicit `DocumentFile` type.
- `DocumentFile` enumerates supported fields; no generic plugin extension-data map is present.
- `ElementId` is a numeric document-local ID. `Document.next_id` allocates IDs for elements, layers and symbols.
- `Element` has an `ElementId`, name, transform and kind; it has no persistent incarnation token.
- `Session.revision` is bumped on document changes, undo and redo.
- `StateId` identifies document content and can identify a historical state restored by undo.

These facts make a numeric element ID alone insufficient as a durable cross-document target reference, and make a restored `StateId` insufficient as the sole stale-result guard.

## 3. Identity model

### 3.1 Persistent document identity

Add a host-owned, persistent, opaque 128-bit `DocumentId` to the serialized document envelope.

Conceptual type:

```text
DocumentId = OpaqueId128
```

Requirements:

- Generated by AniCraft when a new document is created.
- Stored in the document file and preserved by ordinary save, reopen and file relocation/rename.
- Not derived from file path, filename, title, timestamps, artwork fingerprints or `StateId`.
- Immutable for the lifetime of that document identity.
- Validated as non-zero and syntactically canonical.
- Used to scope every persistent FDM target reference.

A 128-bit opaque identifier is a format-level requirement, not a mandate to use a particular Rust crate or UUID version. The host implementation must use a collision-resistant OS-supported generator and test generation failure explicitly.

### 3.2 Target incarnation identity

A target reference consists of:

```text
TargetRef {
  document_id: DocumentId,
  element_id: ElementId,
  incarnation_id: OpaqueId128
}
```

The incarnation token identifies one lifetime of one element ID. It is distinct from geometry revision, topology revision and transform revision.

Recommended storage: a host-owned target-identity ledger in the document extension, mapping live element IDs to incarnation tokens. The ledger is created lazily for existing documents when an FDM target is first registered. It is not necessary to add a new field to every `Element` in the initial design.

Lifecycle rules:

- First registration of a live target allocates a fresh incarnation token.
- The token remains unchanged through ordinary geometry, transform, style, timeline and name edits.
- Deleting a target removes its live identity entry. FDM definitions that still reference it become unresolved/dangling and are diagnosed; they are not silently rebound.
- If an element ID is ever reused, the new live element receives a new token. The old reference therefore cannot resolve to the new element.
- Recreating an element with the same visible name or identical geometry does not restore its old identity.
- If the host can prove `ElementId` is globally monotonic and never reused even across undo, import and reload, the ledger may be optimized later; correctness must not depend on that assumption.

The token is opaque. FDM must not parse it, order it, infer creation time from it or generate it independently.

### 3.3 Revision stamps are not identity

The following concepts remain separate:

| Concept | Purpose | Persistent? | Undo/redo behavior |
|---|---|---:|---|
| DocumentId | Distinguish document identity | Yes | Restored with same document |
| ElementId | Locate element in one document | Yes | Restored as part of document |
| IncarnationId | Distinguish target lifetime | Yes | Restored with that target incarnation |
| Geometry/topology revision | Detect relevant source changes | Prefer host-maintained runtime epoch; persistent only if needed for reopen/cache | Must advance after undo/redo changes |
| Transform/hierarchy revision | Detect changed coordinate dependencies | Host-maintained epoch or explicit fingerprint | Must advance after undo/redo changes |
| Session revision/evaluation epoch | Reject late work | Runtime only | Monotonically advances; never restored |
| StateId | Identify document content for existing host caches/history | Existing host mechanism | May return to an earlier value on undo |

An identity token answers “is this the same target lifetime?” A revision stamp answers “is the input content still the same?” Neither substitutes for the other.

## 4. Host-owned document extension

### 4.1 Placement

Add one dedicated, host-owned FDM extension field to the AniCraft document serialization boundary. It belongs to `Document` and its explicit `DocumentFile` representation, and participates in normal document save/load, equality/dirty-state detection, command snapshots, undo and redo.

The design does not assume an existing arbitrary extension map. It does not place authoritative authored state in plugin installation folders, process memory, editor preferences or a file-path-derived sidecar.

### 4.2 Logical envelope

The following is a logical schema, not implementation-ready Rust source:

```text
FdmDocumentExtension {
  envelope_version: u32,
  document_id: OpaqueId128,
  target_identities: Map<ElementId, OpaqueId128>,
  authored_payload: OpaqueVersionedPayload,
  retained_bake_records: Optional<OpaqueVersionedPayload>
}
```

Ownership:

| Field | Owner | Responsibility |
|---|---|---|
| envelope_version | AniCraft | Extension container compatibility |
| document_id | AniCraft | Persistent document identity |
| target_identities | AniCraft | Live target incarnation mapping |
| authored_payload | FDM schema, hosted by AniCraft | Authored FDM models, target references and FDM-specific schema version |
| retained_bake_records | FDM schema, hosted by AniCraft | Provenance and retained source records for explicit bake |

The opaque payload must carry its own FDM schema version. AniCraft validates the outer envelope and target-identity ledger; FDM validates its internal authored schema and semantics.

### 4.3 Serialization and compatibility rules

- Documents without an FDM extension deserialize as having no FDM data. Their existing behavior and serialized content remain unchanged except for the one-time document-ID migration described below.
- The extension is omitted from serialization when it is truly empty and no FDM identity/payload needs persistence.
- A document ID must still be persisted for any document that contains FDM records or target identity entries.
- The host must not deserialize an unknown FDM payload into a lossy partial structure and then reserialize it.
- If the outer envelope version is unsupported, the host preserves the opaque extension bytes and opens the rest of the document with FDM features disabled/read-only, or reports a clear compatibility error if safe preservation is impossible.
- If the FDM payload version is unsupported, the host preserves it without interpreting or mutating it. FDM authoring/evaluation is disabled until a supported migration is available.
- Unknown fields inside a versioned payload are governed by that payload version's explicit policy. A version that promises strict schema rejects unknown required fields; it must not silently drop them on save.
- Payload size limits, parsing depth, element count and resource limits are enforced before allocation/evaluation. Limits are versioned and tested.
- Migration is deterministic for content transformations. Generating a missing persistent identity is a one-time host migration whose generated value is stored before it can be referenced by FDM data.

### 4.4 Ownership boundary

AniCraft owns:
- the field and file encoding;
- document identity creation;
- target identity assignment and removal;
- document duplication/import remapping;
- extension transaction and dirty-state integration;
- safe preservation of unsupported opaque payloads.

FDM owns:
- authored model schema and validation;
- topology and deformation records;
- semantic migrations between FDM payload versions;
- target-reference interpretation and diagnostics;
- retained deformation provenance semantics.

Neither side may independently invent or mutate the other's identity fields.

## 5. Document identity lifecycle

| Operation | DocumentId | Target incarnation tokens | FDM references |
|---|---|---|---|
| New document | Generate new ID | None until targets are registered | New definitions reference current document |
| Save / autosave | Preserve | Preserve | Preserve |
| Reopen | Restore from file | Restore from file | Resolve against restored identities |
| Rename / move / ordinary Save As to new path | Preserve | Preserve | Preserve |
| Explicit Duplicate / Save As Copy | Generate new ID | Copy tokens for copied targets, unless host remaps IDs; if remapped, rewrite ledger consistently | Internal references remap to new document and target IDs; external document refs rejected |
| Import elements into another document | Destination ID remains | Allocate fresh destination incarnation tokens | Imported FDM records remap only when imported as a complete supported subgraph |
| Import without FDM metadata | Destination ID remains | Allocate tokens on later FDM registration | No FDM records are inferred |
| Delete target | Preserve | Remove live mapping | References become unresolved; no automatic retarget |
| Recreate target | Preserve | Generate fresh token | Old references remain unresolved |
| Undo deletion | Preserve | Restore snapshot's prior token | Old references resolve again to restored target |
| Redo deletion | Preserve | Remove mapping again | References unresolved again |

Clarifications:

- “Save As” is ambiguous in user interfaces. The host must distinguish ordinary relocation/rename from an explicit “duplicate document” or “Save a Copy” operation. Only the latter creates a new DocumentId.
- A full-document duplicate may preserve ElementId values because they are scoped by the new DocumentId. Internal FDM references remain valid after their document scope is remapped. If the duplicate operation remaps element IDs, it must rewrite both the identity ledger and every internal FDM reference atomically.
- Partial import cannot copy references to elements that were not imported. Either the complete referenced FDM subgraph is imported and remapped, or the imported FDM record is rejected/quarantined with a diagnostic.
- Cross-document live target references are unsupported in the first host slice.

## 6. Undo, redo and transaction semantics

### 6.1 Persistent state

The extension envelope, target identity ledger and authored FDM payload are document state. They participate in the same snapshot, dirty-state, save and transaction behavior as other document data.

A failed command restores the full document including the extension. An FDM metadata edit is a document mutation, not a plugin preference update.

### 6.2 Runtime freshness epochs

Runtime freshness counters are not stored in undo snapshots as restorable values.

The host must maintain a monotonic session/evaluation generation that advances on:
- every committed document mutation that can affect an FDM dependency;
- undo and redo;
- document replacement/reopen;
- switching the active document/session instance;
- target deletion/recreation;
- changes to any external sampled input consumed by FDM.

When undo restores old content and an old `StateId`, the runtime generation still advances. Any task captured before the undo is rejected, even if its content fingerprint happens to match the restored state.

### 6.3 Target identity on rollback

- A failed command that is fully rolled back must leave the pre-command target identity ledger unchanged.
- A successful delete removes the target's live identity entry as part of the same transaction.
- Undo restores the prior target and its prior incarnation token.
- Redo removes it again.
- A new creation after undo/redo gets a fresh token unless it is a redo restoring the exact historical snapshot.
- Runtime evaluation generations still advance for all these transitions.

### 6.4 Atomic extension edits

Any command changing both artwork and FDM extension data must be one host transaction. There must be no state in which a target is deleted but its identity entry remains live, or a new target exists with an old target's incarnation token.

## 7. Revision ownership and invalidation contract

The identity design depends on a mutation audit. Before implementation, AniCraft must inventory every command and code path that changes the following:

| Dependency | Examples | Required invalidation |
|---|---|---|
| Source geometry | Path commands, point edits, shape conversion, native Warp apply | Geometry revision/fingerprint changes |
| Topology | Path command structure, control-point insertion/removal, closure changes | Topology revision/fingerprint changes |
| Local transform | Position, rotation, scale, skew, pivot | Transform dependency changes |
| Hierarchy | Layer parenting, reparent, ancestor transform or deletion | Affected descendant dependency changes |
| Timeline sample | Frame/keyframe/tween edits, playhead/time context | Sample identity or sampled-value fingerprint changes |
| Native Asset Warp | Rest path, pins, resolution, applied path | Native Warp dependency changes if consumed |
| FDM model | Parameters, topology, bindings, policy, graph | Authored model revision/fingerprint changes |
| Target lifecycle | Create, delete, import, duplicate | Incarnation identity changes as defined above |

Revision counters are host-owned. FDM receives immutable stamps and fingerprints; it does not increment or repair them.

For v1, a conservative session-wide evaluation generation plus canonical dependency fingerprints is acceptable if the host cannot yet guarantee complete target-level revision coverage. Finer-grained epochs are an optimization, not a prerequisite for correctness.

## 8. Target reference resolution algorithm

The host resolves a target reference in this order:

1. Verify the referenced DocumentId equals the current document identity.
2. Find the ElementId in the current evaluated/document context.
3. Find its live incarnation token in the host-owned ledger.
4. Compare the token exactly with the reference's incarnation token.
5. Verify the target kind and requested operation are supported.
6. Capture source geometry, transforms and all declared dependencies atomically.
7. Return a typed immutable snapshot plus its complete dependency stamp.

Failure at any step is a typed error. The host must not resolve by element name, geometry equality, nearest target, numeric ID alone or stale selection.

The FDM core receives the resolved snapshot and never performs host lookup itself.

## 9. Required conformance tests

These tests refine FDM-06.3 Gate A and Gate B. They must run in AniCraft's actual document serializer, command, history and import/duplicate paths.

| ID | Test | Expected result |
|---|---|---|
| FDM-IDENT-001 | New document identity | Every new document receives a non-zero unique DocumentId |
| FDM-IDENT-002 | Save/reopen | DocumentId and live target incarnation tokens survive round-trip |
| FDM-IDENT-003 | Legacy document migration | Existing files without identity open; one identity is assigned and persisted before FDM references are created |
| FDM-IDENT-004 | Ordinary Save As/rename | DocumentId remains unchanged |
| FDM-IDENT-005 | Duplicate / Save a Copy | New DocumentId; internal FDM target references remain valid after atomic remapping |
| FDM-IDENT-006 | Partial import | Imported elements receive destination identities; absent referenced elements do not resolve |
| FDM-IDENT-007 | Delete/recreate same numeric ElementId | New incarnation token differs; old target reference is rejected |
| FDM-IDENT-008 | Delete/undo/redo | Undo restores prior target identity; redo removes it; runtime freshness epoch always advances |
| FDM-IDENT-009 | Failed delete/create transaction | Rollback restores document and identity ledger exactly |
| FDM-IDENT-010 | Unknown outer extension version | FDM data is preserved opaque or document reports a safe compatibility error; no silent rewrite |
| FDM-IDENT-011 | Unknown FDM payload version | FDM editing/evaluation is disabled; opaque payload survives save/reopen |
| FDM-IDENT-012 | Corrupt/oversized extension | Bounded failure; no panic, partial registration or unbounded allocation |
| FDM-IDENT-013 | Cross-document target reference | Rejected unless a future explicit cross-document contract exists |
| FDM-IDENT-014 | Duplicate identity token | Duplicate live incarnation token within one document is rejected |
| FDM-IDENT-015 | Transform-only edit | Target identity remains stable while transform dependency changes |
| FDM-IDENT-016 | Geometry-only edit | Target identity remains stable while geometry/topology dependencies change |
| FDM-IDENT-017 | StateId restoration | An async result captured before undo is rejected even if undo restores its prior StateId |
| FDM-IDENT-018 | Multi-target atomic extension mutation | Artwork, identity ledger and FDM payload commit or roll back together |

## 10. Migration plan

### M0 — Existing documents without FDM

- Deserialize with the FDM extension absent.
- Preserve existing document behavior.
- Assign DocumentId lazily when a persistent FDM feature first needs it, or during an explicit format migration that is guaranteed to be saved.
- Do not force every existing document to be rewritten merely because FDM support is installed.

### M1 — First FDM-enabled document

- Allocate and persist DocumentId.
- Create the extension envelope at its initial supported version.
- Allocate target incarnation tokens for referenced live elements.
- Validate that every authored target reference resolves before enabling evaluation.
- Save atomically with the host document.

### M2 — Future envelope/payload migrations

- Host migrates only envelope/identity fields it owns.
- FDM migrates only its authored payload schema.
- Migrations are named, ordered and deterministic for content transformations.
- A failed migration leaves original bytes intact and the document recoverable.
- No migration silently rebinds a missing target to a similarly named or geometrically identical element.

## 11. Explicit non-goals

This design does not authorize:
- AniCraft source modifications;
- adding the proposed fields or identity ledger;
- implementing the FDM evaluator or shared DisplayList seam;
- changing ElementId allocation or history implementation;
- target revision implementation across every mutation command;
- native Asset Warp + FDM composition;
- Smart Controller + FDM composition (CCC-01.5 remains unchanged);
- bitmap/text/symbol/group deformation;
- asynchronous scheduling or frame-range bake;
- PR merge.
